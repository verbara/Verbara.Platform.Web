## Context

Child change of the cross-repo `openapi-typed-client` train (host: Verbara.Platform,
`decision_ref: Platform/ADR-0035`). Web is the **decoupled consumer** (buildOrder 2) of
the OpenAPI document the Platform host child publishes as a CI artifact. The contract is
fixed upstream by `Verbara.Platform/openspec/changes/openapi-typed-client/impact.yaml` and
the golden envelope fixture `fixtures/openapi-document.v1.sample.json`; this repo consumes
it (API-first).

Current state: zero codegen tooling in this repo (no `openapi`/`swagger`/`orval` hits in
`package.json`), no generated `.d.ts`, no response validation at the API layer. All wire
types are hand-written interfaces colocated with their hooks — 62 files, ~277
declarations. `src/core/api/client.ts:222-283` (`customFetch<T>` / `customFetchWithHeaders<T>`)
is the single funnel every hook already goes through with a generic `<T>`; this is the
integration point codegen output plugs into with no call-site plumbing.

The motivating drift: `CsatQueueSummary` in `src/core/api/hooks/use-analytics.ts:518-525`
is a hand-written mirror of the real `CsatResponseDto` (Platform). It happens to match
today, but nothing enforces that beyond code review — the exact gap PR#159 fell into for a
different hook (v3.13.1-web).

## Goals / Non-Goals

**Goals:**

- Stand up `openapi-typescript` codegen that turns Platform's exported OpenAPI document
  into a single generated TypeScript declaration file.
- Wire that file into the existing `tsc -b` gate (`build` CI job) so any drift between a
  consumed type and the real document is a compile error, not a silent runtime mismatch.
- Migrate the first hook slice (`use-analytics.ts`'s CSAT surface) off its hand-written
  interface onto the generated type, proving the swap-the-T mechanism end-to-end.
- Leave a clear, low-friction path (documented in tasks.md) for migrating the remaining 61
  hook files in later phases of this same capability.

**Non-Goals:**

- Migrating all 277 declarations in this child — phased; only the CSAT slice ships here.
- Designing or changing any Platform endpoint/DTO shape — the host child (Platform,
  buildOrder 1) owns the document; this child only consumes it.
- Runtime response validation (e.g. zod schemas derived from the OpenAPI document) — the
  generated types are compile-time only, matching the existing `customFetch<T>` contract
  (it already does no runtime validation).
- The realtime SignalR boundary. `src/core/realtime/platform-hub.ts`'s 4 hand-written hub
  payload interfaces (`PresenceUpdatedPayload`, `SupervisionStartedPayload`,
  `WhisperReceivedPayload`, hub connection state) are untouched — hub messages have no REST
  paths and are not representable in an OpenAPI document. That boundary is ADR-0020's
  deferred follow-up (owner: Pro); explicitly out per impact.yaml's scope boundary.

## Decisions

- **Codegen tool: `openapi-typescript`.** Generates types-only output (no runtime client,
  no axios/fetch wrapper) — a clean fit since this repo already owns its fetch layer
  (`client.ts`) and does not want a second HTTP abstraction. Alternatives considered:
  `orval` (generates hooks + client code, which would fight the existing TanStack Query
  hook layer instead of slotting under it) and hand-rolled JSON-Schema-to-TS (reinvents a
  well-maintained tool for no benefit). Rejected both in favor of the narrowest tool that
  does exactly the type-generation job.

- **Delivery mechanism: committed generated file, refreshed by an npm script — not a
  CI-time fetch.** The generated file
  (`src/core/api/generated/openapi.d.ts`) is checked into the repo and regenerated by
  `npm run generate:api-types`, which points at a local copy of the OpenAPI document (dev:
  the running Platform host's `/openapi/v1.json`; CI/offline: the artifact the Platform
  host child publishes). Rationale: this repo's `build` job has no dependency on a live
  Platform instance today (`vite.config.ts:29-31`'s dev proxy is dev-only), and a
  CI-time fetch would newly couple every Web CI run to Platform's artifact being
  reachable/versioned-correctly at build time — a much bigger blast-radius change than
  this child's scope. A committed file also makes drift reviewable in a PR diff (the same
  property the verbatim-fixture-citation rule protects for hand-written DTOs). Trade-off:
  the committed file can go stale between Platform releases — mitigated by a task-level
  script + this design decision being visible, and re-evaluated once the host CI artifact
  publication exists (Platform buildOrder 1) — a live-fetch mode can be added as a
  non-breaking follow-up without changing this decision's consumer-side contract.

- **Consumed contract is the OpenAPI document itself, not individual hand-declared
  shapes.** Per the cross-repo NO-FIXTURE-NO-CONSUME rule, this child does not hand-declare
  any additional wire shape beyond what the golden fixture's envelope describes. The only
  concrete schema in the fixture — `CsatResponseDto` — is the only endpoint shape this
  child migrates (`use-analytics.ts`). Every other of the 277 declarations stays
  hand-written in this child; migrating them means generating from the real document (once
  published) and diffing structurally against the existing hand-written interface — no new
  fixture needed because the document itself, once available, is authoritative for all of
  them at once.

- **Swap-the-T at the call site, not a new abstraction.** `useCsatQueueAnalytics` keeps its
  shape (`customFetch<T>({ url, method })`); only the `T` changes from the hand-written
  `CsatQueueSummary` to the generated
  `components['schemas']['CsatResponseDto']` (re-exported under a local alias for
  readability at the call site). No change to `client.ts` itself in this child.

## Risks / Trade-offs

- **Committed generated file drifts from the real Platform document between refreshes** →
  mitigated by keeping the refresh a one-command script (`npm run generate:api-types`) run
  whenever Platform's contract changes, and by the `tsc -b` gate catching any downstream
  type mismatch introduced by a stale-vs-hand-written seam during the phased migration.
  Fully closing this risk (CI-enforced freshness check) is a candidate for a later phase
  once the Platform host CI artifact exists — not blocking for this child.
- **Partial migration leaves two type sources of truth (generated + hand-written) during
  the phased rollout** → scoped explicitly: only `use-analytics.ts`'s CSAT surface migrates
  here; the remaining 61 files are unambiguously tracked as follow-up tasks in tasks.md, not
  silently left ambiguous.
- **API-first dependency**: the generated file's initial content depends on Platform
  actually publishing `/openapi/v1.json` reliably (buildOrder 1, host child) — until then,
  this child's codegen script runs against a local/dev instance or the golden fixture
  shape for the CSAT slice specifically, which is already known verbatim.
- **Structural-vs-nominal type mismatch risk during swap**: generated types are structural
  (`type`, not `interface`); a hook consuming the old nominal `CsatQueueSummary` name
  elsewhere (e.g. in a component prop type) needs its import updated too → mitigated by
  grepping for `CsatQueueSummary` usages as an explicit task before removing the old
  interface.

## Migration Plan

Additive + one narrow swap — no breaking changes to `useCsatQueueAnalytics`'s consumer
call sites (the generated `CsatResponseDto` type is structurally identical to the
hand-written `CsatQueueSummary` it replaces: same 6 fields, same names, same wire types).
Re-pin 3.13.1-web → 3.14.0-web per impact.yaml's tentative next-minor target. Rollback =
revert the branch; the generated file and codegen script are additive, and the
`use-analytics.ts` swap is a pure type-level change (no runtime behavior change), so
reverting drops cleanly back to the hand-written interface.

Remaining 61 hook files migrate in later phases of the same `openapi-generated-types`
capability, each phase scoped to a natural grouping (e.g. by module: Admin, Agent,
Analytics, Operations), each gated the same way (`tsc -b` catches drift) — tracked as
follow-up tasks, not follow-up changes, since the mechanism this child establishes does
not change per phase.

## Open Questions

None. Per the NO-FIXTURE-NO-CONSUME rule, this child's only consumed concrete wire shape
(`CsatResponseDto`) is fully specified by the golden fixture, and the codegen delivery
mechanism (committed file vs CI fetch) is settled above as a Decision, not deferred. Any
durable architectural decision arising from a later migration phase would be recorded as
an ADR under `Verbara.Platform/docs/decisions/` per the shared-workstream rule, not as an
open question here.

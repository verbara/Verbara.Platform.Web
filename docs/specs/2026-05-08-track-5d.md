## Problem

After 5A/5B/5C-a11y/5C-export, three UX gaps remain in Nivel 5:

1. **Required field indicators are invisible.** `<Label>` got a `required` prop in Track 5C-a11y (visible asterisk + sr-only "required") but only ~4 Label instances use it today. Users can't tell which fields are required without trying to submit. Track 5C-a11y migrated 8 Tier 1 forms to `useFieldA11y` + `<FieldError>` + `<Label required>`; ~70 Tier 2/3 forms still lack the a11y plumbing AND the visible required marker.
2. **No tenant context indicator in normal state.** During impersonation, the `ImpersonationBanner` shows the target tenant. But day-to-day, an operator on a multi-tenant deployment has no on-screen reminder of which tenant they are operating against. The mistake mode (acting on the wrong tenant) is silent today.
3. **Permission-denied actions are invisible, not disabled.** `<PermissionGuard>` (used 238× across the codebase) returns `null` when the user lacks the required permission. Action buttons in admin pages disappear entirely instead of showing as disabled with an explanation. New users can't tell whether a feature exists but is gated, or doesn't exist at all. ~120 of those usages are action-level (buttons inside row toolbars, headers, form footers); the remaining ~118 are route-level guards with `redirect=true` which should keep their hide-and-redirect behavior.

This is the closure track for Nivel 5 — UX Maturity.

## Goals

1. **Required asterisks visible everywhere they apply.** Bulk-migrate `<Label>` instances across all forms to add `required` based on the corresponding Zod schema (a field NOT marked `.optional()` / `.nullish()` is required).
2. **Tier 2/3 forms reach a11y baseline.** Extend the `useFieldA11y` + `<FieldError>` + `<Label required>` pattern from Track 5C-a11y's 8 Tier 1 forms to all remaining ~70 forms. After this track, every form in the app has the same a11y plumbing.
3. **Persistent tenant identity in the rail.** A small `<TenantBadge>` next to `UserMenu` shows the active tenant's name. Distinct visual state during impersonation to coordinate with the existing red banner.
4. **Disabled-with-tooltip permission UX for action buttons.** A new `<PermissionButton>` primitive — the user sees the action exists but is gated, with the missing permission listed in the tooltip.

## Out of Scope (explicit)

- **Tenant switcher dropdown** (clickable badge that lets a superadmin change tenants). Read-only badge only this track. Switcher is a separate feature with its own permission flow + cross-tenant data hygiene concerns.
- **Form abandonment warnings** ("you have unsaved changes — leave anyway?"). Defer.
- **Async field validation** (uniqueness checks via API calls during typing). Defer.
- **Form-level error summary** (aggregate banner at top listing all errors). Already deferred from 5C-a11y, stays deferred.
- **Multi-step wizard UX standardization.** Out of scope.
- **`<PermissionGuard mode="disable">` second mode.** YAGNI — `<PermissionButton>` covers the action-button cases (~120 of 238 usages); section/card-level "disabled with reason" UX is rare and can ship if a real case surfaces during implementation.
- **Permission-denied tooltip translation of permission codes** (e.g., `users:user:delete` → "Delete users"). Tooltip shows the raw permission code for now; humanizing the codes is a separate i18n task.

## Architecture

### Unit 1 — `src/core/ui/permission-button.tsx`

A thin wrapper over `<Button>` + `<Tooltip>` + `useHasPermission` / `useHasAnyPermission` from `src/core/auth/use-has-permission.ts`.

```tsx
import type { ComponentProps, ReactNode } from 'react';

interface PermissionButtonProps extends Omit<ComponentProps<typeof Button>, 'disabled'> {
  /** Single permission required (mutually exclusive with `requiresAny`) */
  requires?: string;
  /** Any of these permissions allowed */
  requiresAny?: string[];
  /** Force-disable from caller (passes through to underlying Button) */
  disabled?: boolean;
  /** Children = button content */
  children?: ReactNode;
}
```

Behavior:

- If permission missing: button rendered with `disabled` + wrapped in `<Tooltip>` whose content is the i18n string `permission.button.requires` interpolated with the permission(s).
- If permission allowed: passes through to `<Button>` unchanged. If `disabled` was provided by the caller, that takes precedence.
- The tooltip wrapping is conditional — when allowed, no extra DOM. When denied, wraps the button so hover/focus reveals the tooltip even though the button itself is disabled (Tooltip's trigger sits on a focusable wrapper element in @base-ui's pattern).

A11y:

- Disabled button gets `aria-describedby` pointing to the tooltip ID.
- The tooltip uses `role="tooltip"` (default in @base-ui).
- Keyboard users can Tab to the disabled button (it remains focusable via `aria-disabled` instead of native `disabled` to keep tooltip accessible — this is the standard pattern). Implementation note: use `aria-disabled="true"` + manual click prevention rather than HTML `disabled`, otherwise the disabled element is removed from focus order and the tooltip can't reach it via keyboard.

### Unit 2 — `src/core/ui/tenant-badge.tsx`

Reads tenant context from `useTenantStore` and `useTenant(activeTenantId)`. Composes with existing `<Badge>` + `<Tooltip>`.

```tsx
interface TenantBadgeProps {
  /** Visual size — `sm` matches rail compact icons; default `default` */
  size?: 'sm' | 'default';
}
```

Behavior:

- Reads `activeTenantId` from `useTenantStore`.
- Reads tenant via `useTenant(activeTenantId)` — same hook used in 5C-export's `<PdfDownloadButton>`. Cached query so no extra fetch on rail mount.
- Reads impersonation state from `useAuthStore` (`s.impersonation`).
- Renders:
  - Normal state: `<Badge variant="secondary">` with `<Building2>` lucide icon + truncated tenant name (max ~14 chars in rail). Full tenant name + ID in tooltip.
  - Impersonation state: `<Badge variant="secondary">` with amber tint via custom class + `<Shield>` icon — coordinates with the red ImpersonationBanner already at top.
- A11y: `aria-label={t('tenant.badge.tooltip', { name: tenant.name, id: tenant.tenantId })}`.
- Loading state: while `useTenant` resolves, shows `<Skeleton variant="text" className="w-20 h-5" />`. Almost never visible after first render thanks to TanStack Query cache.

**Placement:** Inside `src/shell/rail.tsx`, in the bottom segment that already houses `<NotificationBell>` and `<UserMenu>`. New order (top→bottom of bottom group): `<TenantBadge size="sm">` → `<CommandPaletteIcon>` → `<NotificationBell>` → `<UserMenu>`.

The rail today is a vertical 12-px-wide column. The `TenantBadge` `sm` variant is a compact circle/icon with the tooltip carrying the full name. Clicking the badge does NOTHING (read-only this track). A future "tenant switcher" track can give it a `Popover` for cross-tenant navigation.

### Unit 3 — Required asterisk migration (no new code, mechanical edits)

**Driver:** the Zod schema is source of truth. For each form file:

1. Read its Zod schema.
2. For each field NOT marked `.optional()` / `.nullish()` / `.default(...)`, the corresponding `<Label>` for that field gets `required`.
3. Edit. Done.

**Scope:**

- 16 dedicated `*-form.tsx` files (admin domain forms).
- ~10 page-level forms (auth pages + agent steps + a few admin pages without dedicated form file).
- 8 forms already migrated by Track 5C-a11y stay as-is — verify they still have correct asterisks.

This unit produces ~120-200 small Label edits across ~26 files.

### Unit 4 — Tier 2/3 form a11y migration (mechanical edits)

For each remaining form:

1. Import `useFieldA11y` from `@/core/hooks/use-field-a11y`.
2. For each `Controller`-rendered or RHF-registered field, derive an `errorId` and pass `inputProps` to the input.
3. Replace inline `<p className="text-destructive">{errors.field?.message}</p>` with `<FieldError id={errorId} message={errors.field?.message?.toString()} />`.
4. Add `required` to the `<Label>` per the schema.

**Scope:** ~70 forms. This is the bulk migration. Best done in subagent batches by domain (admin/agents, admin/billing, admin/queues, admin/users, admin/flows, admin/notifications, admin/security, admin/system, agent/\* etc).

**Compatibility:** Some forms wrap `Controller` for Base UI Select/Checkbox primitives that don't forward `aria-*` props through `render` callbacks. For those, document inline the limitation (carry-over from 5C-a11y R2 risk) and migrate what _is_ migratable. Avoid over-engineering Controller wrappers in this track.

### Unit 5 — `<PermissionButton>` migration

Find every `<PermissionGuard requires="..."><Button .../></PermissionGuard>` pattern and replace with `<PermissionButton requires="...">`.

Heuristic: any `<PermissionGuard>` wrapping a single `<Button>` (or `Button`-shaped element) is a candidate. PermissionGuards wrapping multiple children, sections, or with `redirect=true` stay as-is.

Subagent batched by area: admin/users, admin/agents, admin/billing, admin/tenants, agent/\*, etc.

## Risks & Mitigations

| Risk                                                                                                       | Likelihood | Mitigation                                                                                                                       |
| ---------------------------------------------------------------------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `aria-disabled` + manual click prevention regression on `<PermissionButton>`                               | M          | Unit test asserts both: no fire of onClick handler when disabled, and Tab still focuses (preserves tooltip access)               |
| Bulk Label migrations skip a required field whose Zod schema uses `.refine()` instead of plain `.string()` | M          | Audit pass: `grep -rE 'z\.refine\|\.refine\(' src/admin/` then manual review of those forms                                      |
| Tier 2/3 a11y migration introduces hooks-rules violations (Controller render callbacks)                    | M          | Use `useFieldA11y` outside Controller's render prop; pass `inputProps` via render callback's `field` argument                    |
| TenantBadge fetch fails for orphan `activeTenantId` (e.g., tenant deleted)                                 | L          | Falls back to displaying the raw tenantId — already handled by 5C-export pattern                                                 |
| ImpersonationBanner + TenantBadge double-render confusing                                                  | L          | Different visual hierarchies: banner is full-width red top bar; badge is small in-rail amber chip. Distinct affordances          |
| 80–120 PermissionButton migrations break unit tests that mock PermissionGuard                              | M          | Migration scripted per-file; tests for migrated areas re-run after each batch                                                    |
| `<PermissionButton>` consumers pass `disabled` AND lack permission — which wins?                           | L          | Explicit precedence: `disabled` from caller takes priority (button stays disabled regardless of permission). Documented in JSDoc |

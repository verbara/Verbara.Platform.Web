# Track 7B — Per-Tenant OIDC SSO Configuration

**Version:** 2.4.0
**Status:** Draft (pending user review)
**Created:** 2026-05-09
**Predecessor:** [Track 6A](2026-05-08-track-6a.md) (closed `v2.3.0-web`); Track 7A closed via [ADR-0008](../decisions/0008-ip-allowlist-per-tenant-tab-over-standalone-page.md)
**Roadmap entry:** [`docs/plans/completed/2026-05-03-v1.14.x-operational-foundation-roadmap.md`](../plans/completed/2026-05-03-v1.14.x-operational-foundation-roadmap.md) §Nivel 7 → Track 7B

## Problem

The roadmap entry calls Track 7B "SAML SSO admin UI" but the audit revealed:

1. **Backend implements OIDC, not SAML.** `OidcEndpoints.cs` provides authorization-code-flow with PKCE, ID token validation, MFA enforcement on callback. No SAML support exists in `PlanFeature` enum or anywhere in `Verbara.Platform.Identity`. The roadmap label is inaccurate; this track is correctly framed as **OIDC SSO admin**.
2. **OIDC login is already working end-to-end.** `login-page.tsx:196-203` has a "Sign in with SSO" button that initiates `/api/v1/auth/oidc/login?tenant_id=…`; the callback handler at `login-page.tsx:57-105` extracts the JWT from a URL fragment and stores it via `auth-store`. MFA is enforced server-side in `OidcEndpoints.cs:214-242`.
3. **Per-tenant OIDC config is supported by the backend but not by the Web UI.** The backend's `PATCH /api/v1/management/tenants/{id}/settings` accepts an `auth` payload that includes `oidcEnabled`, `oidcAuthority`, `oidcClientId`, `oidcClientSecret`, `oidcAutoCreateUsers`, and `oidcDefaultRole`. The Web UI exposes only `oidcEnabled` (a checkbox in `tenant-settings-form.tsx:319-329`), forcing tenants to inherit a single platform-wide `Authority`/`ClientId`/`ClientSecret` configured at `/admin/system/auth-config-page.tsx`. There is no UI for a tenant to point at a different identity provider.

## Goals

1. **Per-tenant OIDC configuration UI** — a new SSO tab inside `tenant-detail-page` that exposes all OIDC fields (`oidcEnabled`, `oidcAuthority`, `oidcClientId`, `oidcClientSecret`, `oidcAutoCreateUsers`, `oidcDefaultRole`) so each tenant can plug in its own IdP.
2. **Feature-gate by `OidcSso` plan feature** — same pattern as `<IpAllowlistTab>`: read `enabledFeatures.includes('OidcSso')` from tenant settings and show an upgrade message when disabled.
3. **Test login link** (Tier 2 stretch) — a "Test sign-in" button that opens `/api/v1/auth/oidc/login?tenant_id=…&return_url=…` in a new tab so the admin can verify the configured IdP works without affecting their current session.
4. **Roadmap label correction** — update the Track 7B entry to read "OIDC SSO" (not "SAML SSO").

## Out of Scope (explicit)

- **SAML support.** Backend doesn't implement it. If demand emerges, opens a separate cross-cutting track with backend coordination.
- **Standalone `/admin/security/sso` page.** Per [ADR-0008](../decisions/0008-ip-allowlist-per-tenant-tab-over-standalone-page.md), per-tenant features live in tenant-detail tabs. SSO config is per-tenant by data model. A standalone page would either duplicate the tab or require a backend cross-tenant aggregation endpoint (does not exist).
- **OIDC discovery preview** (live-fetching `${authority}/.well-known/openid-configuration` and rendering discovered endpoints). Tier 3 — nice UX validation but adds complexity (CORS proxy, error states) for marginal value. Defer.
- **Attribute claim → role mapping UI.** Backend exposes only `oidcDefaultRole` (single fallback role); fine-grained claim mapping requires backend schema expansion. Defer.
- **Multiple OIDC providers per tenant.** Backend stores one provider per tenant. Multi-provider is a separate cross-cutting track.
- **Migrate platform-wide `auth-config-page.tsx` to per-tenant only.** Out of scope. Platform-wide defaults remain useful for new tenants that haven't customized; per-tenant overrides take precedence at runtime.
- **Certificate pinning, JWK rotation, scope customization, metadata XML upload.** OIDC standards handle these via discovery; backend doesn't expose configuration knobs.
- **Migrating the existing `oidcEnabled` checkbox out of `tenant-settings-form.tsx`.** Keep both surfaces in sync — the SSO tab is the canonical config; the existing checkbox in the Auth section becomes a quick-toggle that mirrors `oidcEnabled`. Optional cleanup deferred to follow-up patch.

## Architecture

### Unit 1 — `src/admin/tenants/use-tenant-settings.ts` extension

Extend the existing `UpdateAuthPayload` type to include `oidcClientSecret`:

```ts
export interface UpdateAuthPayload {
  // ... existing fields ...
  oidcEnabled?: boolean;
  oidcAuthority?: string | null;
  oidcClientId?: string | null;
  oidcClientSecret?: string | null; // NEW — write-only
  oidcAutoCreateUsers?: boolean;
  oidcDefaultRole?: string;
  // ... rest ...
}
```

Backend already accepts the field via `PATCH /api/v1/management/tenants/{id}/settings` (confirmed at `TenantSettingsEndpoints.cs:114` and `:450`). The existing `useUpdateTenantSettings` mutation needs no signature change — it accepts `UpdateAuthPayload` already.

### Unit 2 — `src/admin/tenants/sso-tab.tsx`

```tsx
interface SsoTabProps {
  readonly tenantId: string;
}
```

Component structure:

1. Read `useTenantSettings(tenantId)` (already exists). Extract `auth` and `enabledFeatures`.
2. If `!enabledFeatures.includes('OidcSso')` → render upgrade message (mirror `<IpAllowlistTab>` pattern).
3. RHF form with Zod schema:
   ```ts
   const schema = z.object({
     oidcEnabled: z.boolean(),
     oidcAuthority: z.string().url().nullable().or(z.literal('')),
     oidcClientId: z.string().nullable().or(z.literal('')),
     oidcClientSecret: z.string().optional(), // write-only
     oidcAutoCreateUsers: z.boolean(),
     oidcDefaultRole: z.string().min(1),
   });
   ```
4. Initial values from `auth` slice (oidcClientSecret left blank — backend doesn't return it).
5. On submit: call `useUpdateTenantSettings(tenantId).mutate({ auth: <only-changed-fields> })`. Skip `oidcClientSecret` in the payload if user left it blank (don't overwrite).
6. "Test sign-in" button (Tier 2): only enabled when `oidcEnabled && oidcAuthority && oidcClientId`. On click, opens `/api/v1/auth/oidc/login?tenant_id=${tenantId}&return_url=${encodeURIComponent('/admin/tenants/' + tenantId)}` in a new tab.

Form a11y:

- All required fields use `<Label required>` + `useFieldA11y` + `<FieldError>` (same as the 14 forms migrated in Track 5D).
- `oidcClientSecret` input has type=password with show/hide toggle (mirror existing pattern in `auth-config-page.tsx` if available).
- Helper text under `oidcClientSecret`: "Leave blank to keep the existing secret. Enter a new value to overwrite."
- Status indicator above `oidcClientSecret`: "Secret configured" (✓) if `auth.oidcClientId` is set (proxy for "config has been written") OR a dedicated backend flag if available.

## Risks & Mitigations

| Risk                                                                                                                 | Likelihood | Mitigation                                                                                                                                                                                                                                       |
| -------------------------------------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --- | ---------------------------------------------------------------------------------------------------------------------- |
| User overwrites existing `oidcClientSecret` accidentally by typing a new value (then realizing)                      | M          | Show a confirmation prompt in the toast: "Secret will be replaced — proceed?" Or: defer the overwrite until form save and clear the input on Cancel. Alternative: use `<input type="password">` with placeholder "Enter new value to overwrite". |
| User leaves `oidcAuthority` blank but enables `oidcEnabled` — login flow then breaks                                 | M          | Zod schema requires Authority + ClientId when `oidcEnabled === true`. Refine: `z.refine((data) => !data.oidcEnabled                                                                                                                              |     | (data.oidcAuthority && data.oidcClientId), { message: 'Authority and Client ID are required when OIDC is enabled' })`. |
| Test sign-in button opens login flow but tenant_id query param mismatches active session tenant                      | L          | Pass explicit `tenant_id=${tenantId}` (not the active session); user is testing the configured tenant, which is fine.                                                                                                                            |
| Backend response on save doesn't include the new `oidcClientSecret` (security) — frontend can't show it back         | L          | Expected behavior. UI shows "Configured" indicator based on `oidcClientId` being non-null (proxy). If backend later exposes a `oidcClientSecretConfigured: boolean` flag, switch to that.                                                        |
| `enabledFeatures` doesn't include 'OidcSso' even though backend is willing to accept the config                      | L          | Feature gate is the contract; if a tenant sees the upgrade message but their backend allows the config, that's a billing/plan inconsistency to flag separately. UI respects the feature flag.                                                    |
| Existing `oidcEnabled` checkbox in `tenant-settings-form.tsx` (Auth section) drifts out of sync with the new SSO tab | L          | Both write to `auth.oidcEnabled` via the same endpoint. After save in either surface, TanStack Query invalidates `['tenant-settings', tenantId]` so both surfaces refresh. Documented; cleanup of the duplicate checkbox deferred.               |
| User uses RHF Controller with Base UI Switch/Select; primitives don't forward aria-\* (R2 risk per Track 5C-a11y)    | M          | Same as 14 prior forms migrated in Track 5D — apply the workaround pattern: keep `<Label required>` + `<FieldError>`, document the limitation inline if `inputProps` can't propagate.                                                            |

# Plan — W6 (capacidad): default por-tenant + override por-agente + enforcement real de `MaxTotal` (ADR-0009 north-star, última pista)

## Context

**Por qué:** W6 es la **última** pista del norte ADR-0009 (presencia/sesión/continuidad). Hoy la capacidad por-canal de un agente está **hard-coded** (`ChannelCapacity`: Voice 1 / Chat 3 / Email 5 / SMS 3), `MaxTotal` está **definido pero muerto** (`grep .MaxTotal` = 0 usos de enforcement), y **no hay ninguna forma de configurarla** (los DTOs create/update de agente ni la exponen; ningún editor a nivel tenant). Además el análisis profundo destapó **dos bugs reales de enforcement** que harían que cualquier "editor + MaxTotal" se montara sobre un contador roto:

1. **Bug chat-pool (alta severidad):** `InMemoryAgentCapacityService._load` se indexa por `ChannelType` crudo, pero `GetMax` agrupa toda la familia chat (WebChat/WhatsApp/Messenger/Instagram/Telegram/Twitter/Video/Rcs) en `MaxChat`. Resultado: cada sub-canal cuenta **aparte** contra `MaxChat=3` → un agente puede sostener ~24 chats "respetando" MaxChat=3. Y `PersistCurrentLoadsAsync` solo lee el bucket `WebChat` como "chat" → la carga de chats no-WebChat persiste en 0.
2. **`MaxTotal` nunca se aplica:** `HasCapacityAsync` solo compara `load[canal] < GetMax(canal)`; jamás suma a través de canales.

**Resultado deseado:** capacidad configurable a nivel producto (default por-tenant como fuente de verdad + override esparcido por-agente, resuelto al leer), `MaxTotal` realmente aplicado sobre el agregado **asíncrono** (voz exclusiva), contador de chat correcto, voz fijada en 1 hasta el mixing-bridge ARI (W5b diferido), y auditoría de cambios — entregado cross-repo (Platform + Web) como W1–W5b.

## Decisiones (tras análisis profundo + 3 críticos adversariales + síntesis de diseño; usuario confirmó D1/D2/D3)

- **D1 — Granularidad = default por-tenant + override por-agente** (null = heredar, resuelto al leer; una re-sintonía del tenant = 1 edición, sin backfill). Patrón Connect/Genesys/Five9/Twilio.
- **D2 — `MaxTotal` = voz exclusiva.** `MaxVoice` fijo en 1 (carril aparte, NO cuenta para MaxTotal). `MaxTotal` = techo de la suma async = `chat-pool + email + sms`. Gate de routing: para voz `voiceLoad < MaxVoice`; para canal async `loadPool[canal] < cap[canal]` **Y** `asyncTotal < MaxTotal`.
- **D3 — Robustez plegada (sin atajos):** (a) fix del contador chat-pool en el camino vivo + persistencia; (b) pin Voz=1 (server-side en el resolver + read-only en UI); (c) auditoría de cambios de capacidad (override agente + default tenant).

### Representación + seam (LOCKED, verificado en código)

- **Override (D-A):** nueva clase `ChannelCapacityOverride` (per-field **nullable** `int?`: MaxVoice/MaxChat/MaxEmail/MaxSms/MaxTotal, todos `null` = heredar). Renombrar `Agent.Capacity` → `Agent.CapacityOverride`. **Back-compat gratis:** las filas existentes son `capacity='{}'` jsonb → deserializa a todos-null = "heredar todo" = mismo efecto (los defaults de clase 1/3/5/3/5 = el default tenant sembrado 1/3/5/3/5). **Sin migración de la tabla `agents`.** Radio del rename: 3 sitios (`AgentMeResponseDto:49`, `Agent.HasCapacity` Agent.cs:59-66 — _solo usado en tests_, `InMemoryAgentCapacityService:22`).
- **Resolución (D-B):** `Verbara.Platform.Queues` **no** referencia `Verbara.Platform.Identity` (verificado: solo Core+Conversations) → definir `ICapacityDefaultsProvider` (interfaz en Queues) implementada en `Verbara.Platform.Api` como `TenantAuthConfigCapacityDefaultsProvider` que lee `ITenantAuthConfigStore` (**ya envuelto por `CachedTenantAuthConfigStore`** → caché hot-path + invalidación reusados, sin caché nuevo; fallback hard 1/3/5/3/5 si falta la fila). `IAgentCapacityResolver` (en Queues) = `override.X ?? default.X`, pin `MaxVoice=1`. El resolver **es dueño** de la lectura agente+defaults (evita doble GetById en el hot-path).
- **Storage default tenant (D-C):** columnas snake_case explícitas en `tenant_auth_config` (NO jsonb — evita el mismatch camelCase de `PostgresJsonSerializer`; consistente con `voice_callback_grace_seconds` etc.). **Migración `033_TenantCapacityDefaults.sql`** (`max_voice_default`=1, `max_chat_default`=3, `max_email_default`=5, `max_sms_default`=3, `max_total_default`=5). Editado vía el PUT existente `/admin/tenant/settings` (`AdminOnly`), sección Operational.
- **Denominador MaxTotal (D-D):** `asyncTotal` = misma carga que el `_load` vivo rastrea = conversaciones `Reserve`adas sin `Release` = `ConversationState.Active` (Accept→Reserve; WrapUp/Transfer/ReturnToBot→Release; OnHold/Consulting/Snoozed NO liberan). `ReconcileAsync` ya cuenta solo Active → vivo y persistido concuerdan. `MaxTotal` NO es un `ChannelType` y NO sale de `GetMax`; se suma explícito.
- **Chat-pool (D-E):** `NormalizeToCapacityBucket(ChannelType)` (familia chat → `WebChat` canónico; Voice/Email/Sms → sí mismos) como primera línea de `Reserve/Release/GetCurrentLoad/HasCapacity`. Arreglar `PersistCurrentLoadsAsync` para leer el bucket pooled.
- **Audit (D-F):** dos `IAuditService.RecordAsync` best-effort (patrón try/catch de `ForceAgentOffline`): `agent.capacity_override` (cat `queues`) y `tenant.capacity_default_changed` (cat `operational`), con old/new por-campo + actor. **Sin evento cross-pod nuevo** (no toca `PlatformPushJsonContext` ni el guard SSE — lección W4 N/A aquí). El `AgentCapacityChangedEvent` de load-tracking existente es distinto y no se toca.
- **Diferidos (norte):** voice pre-gate + voz simultánea (>1) → bloqueado en mixing-bridge ARI (W5b diferido); reserve atómico / carrera del último slot (transitorio + reconcile-safe → comentario, sin lock); cards de utilización en wallboard/analytics (W6+1); capacidad per-cola/per-team, programada/time-of-day, lanes VIP, cascada multi-tenant, webhooks; permiso granular `queues:agent_capacity:configure` → se mantiene **`AdminOnly`** (como todas las rutas `/admin/*` de agente).

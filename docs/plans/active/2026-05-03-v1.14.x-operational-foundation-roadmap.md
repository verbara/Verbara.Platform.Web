# Plan Maestro: v1.14.x → v1.21.x — Operational Foundation Roadmap

**Created:** 2026-05-03
**Status:** Active (planning, not yet executed)
**Repo:** `/media/Data/Source/IPcom/Asterisk.Platform.Web/`
**Origin:** Auditoría profunda post-cierre del track v1.13.x i18n. La auditoría reveló 14 áreas críticas omitidas en el roadmap original, incluyendo blockers operacionales (CI/CD, error tracking, coverage, vulnerabilidades) que harían fracasar cualquier track customer-facing si se ejecutan primero.

## Context

El track v1.13.x cerró la calidad i18n (ver [`completed/2026-05-03-v1.13.x-closure-i18n-lint-resilience.md`](../completed/2026-05-03-v1.13.x-closure-i18n-lint-resilience.md)). Una auditoría de 3 ejes paralelos (producto/backlog, postura técnica, madurez UX) reveló que el producto está en **~60/100 production-ready** con gaps no documentados:

- **Cero CI/CD pipeline** — sin gates en PRs, sin automated tests/lint/build
- **Cero error tracking en producción** — operadores ciegos a errores reales de cliente
- **Cero pre-commit hooks** — calidad depende del honor system local
- **Cero coverage tracking** — 205/205 tests pasan pero cobertura desconocida
- **9 vulnerabilidades npm audit** (3 HIGH severity)
- **32 endpoints backend sin hook Web** (Backend-to-UI Bridge gap)
- **Loading states inconsistentes** — 40 archivos con `if (isLoading) return null` (UX roto)
- **Sin virtualization en agent** — colapsa con 500+ mensajes
- **Cero `aria-live` regions** — WCAG-fail para usuarios ciegos
- **Sin README/LICENSE/CONTRIBUTING** — onboarding de devs imposible

La decisión meta es **establecer el piso operacional ANTES de features customer-facing** (ver [ADR-0003](../../decisions/0003-operational-foundation-priority.md)).

## Pirámide de prioridad

```
[v1.20.0+]   Customer features (IP Allowlist UI, SAML SSO, WebChat widget)
            ↑
[v1.18.x]    UX deeper (loading states, virtualization, a11y, print/export)
            ↑
[v1.17.x]    Backend-to-UI Bridge (32 endpoints sin hook)
            ↑
[v1.16.x]    Calidad técnica (lint-2, ts-strict-2, deps majors)
            ↑
[v1.15.x]    Test coverage + perf budget + bundle
            ↑
[v1.14.x]    CI/CD + error tracking + pre-commit + vulns ← EMPEZAR AQUÍ
            ↑
[v1.14.0]    Public docs (README/LICENSE) + migration matrix
```

## Acceptance: production-readiness score

Estado actual: 60/100. Niveles 1-2 sube a 85/100. Niveles 3-7 cierra a 95+/100.

**Threshold strategy — ratchet floor (no 70%):** El roadmap original pedía `lines: 70` desde día 1. Imposible: el baseline real es 12.92% porque los 205 tests cubren mayormente i18n hooks, MFA wizard, error boundary y un puñado de UI primitives — todo lo demás (54 API hooks, stores core, agent inbox, operations wallboard, admin pages) está en 0%. Se fija ratchet floor en valores ligeramente inferiores al baseline (`lines: 12, statements: 12, branches: 13, functions: 10`) para prevenir regresión sin bloquear cleanup. El target 70% es deliverable de Track 2C cuando entren MSW + 50+ hook tests. Patrón análogo al `lint (non-blocking)` del Track 1C.

**Áreas con coverage parcial existente:**

- `src/admin/license` — 84.48% lines (validators tested)
- `src/core/i18n` — 73.68% lines (formatDate/Number tests recientes)
- `src/core/security/mfa` — 72.34% lines (TOTP enroll wizard)
- `src/admin/shared` — 58.49%, `src/agent/stores` — 52.72%, `src/analytics/qa` — 54.12%

**Áreas en 0% prioritarias para Track 2C:**

- `src/core/api/hooks/**` (54 hooks, ~16% via incidental coverage) — más alto ROI por tests directos
- `src/core/auth` — 6.49% — auth/JWT refresh logic, blast radius alto
- `src/core/stores` — tenant/notification/ui/permissions stores en 0%, cheap to test

Acceptance original (70% líneas) **deferred to Track 2C (1.15.5)** una vez MSW + hook tests landen. Ratchet floor sube progresivamente: 12% → 50% (post-2C) → 70% (post-3A) → 80% (post-Tracks 4-5).

## Ritual de cierre por track

Cada track sigue el patrón establecido en v1.13.x:

```sh
# 1. Verificar verde
npm run build && npm run test -- --run && npm run lint && npm run i18n:check
# Tests E2E (cuando aplique): npx playwright test

# 2. Push commits
git push origin main

# 3. Tag annotated con notas del track
git tag -a v<version>-web -m "<resumen>"
git push origin v<version>-web

# 4. GitHub release con notas (gh release create)
# 5. Mover plan: git mv docs/plans/active/<plan>.md docs/plans/completed/
```

Versionado per [ADR-0005](../../decisions/0005-versioning-track-end-tags.md): patches dentro de tracks SIN tag intermedio; solo el último ship del track recibe tag + release.

## Dependencias críticas

1. **Track 1C → todos los demás**: sin CI/CD, los siguientes tracks acumulan riesgo.
2. **Track 1E → Track 5A**: Sentry debe estar en producción antes de meter más UI complejo (loading states, virtualization) para capturar regresiones.
3. **Track 2A → Track 3A**: Coverage tracking antes de refactor de barrel exports (regression detection).
4. **Track 4 → Track 7**: Bridge debe completarse antes de IP Allowlist UI (mismo dominio: tenant settings, security config).

- **Feature flags admin** (`useFeature` system) — defer hasta v2.0
